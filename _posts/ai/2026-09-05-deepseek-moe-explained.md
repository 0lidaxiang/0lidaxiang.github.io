总参数这么大，每次却只激活一部分，MoE 到底怎么把账算过来的？我觉得 DeepSeek 最值得拆开的，就是容量、计算和缓存这几笔账。拆明白以后，那些看着吓人的参数数字就好理解了。

## 先把四个名字分开

从 2024—2025 年的技术报告往下看，DeepSeekMoE 讲专家架构，V2 与 V3 把相关结构带进模型，R1 重点讲推理能力的后训练。先把这几个名字放回各自的位置，后面的工程设计就能串起来。

| 工作 | 阅读重点 |
| --- | --- |
| DeepSeekMoE | 细粒度路由专家与共享专家 |
| DeepSeek-V2 | MoE 与 MLA 的组合 |
| DeepSeek-V3 | 负载均衡、训练目标与系统效率 |
| DeepSeek-R1 | 强化学习、冷启动与推理行为 |

## 总参数和激活参数为什么可以不同

稠密模型的大部分层，对每个 token 都执行相似计算。MoE 常把前馈部分拆成多个专家，由路由器选择其中一部分处理当前 token，再合并结果。

```text
输出 ≈ 共享专家(x) + Σ 被选专家的路由权重 × 专家输出(x)
```

先用这个概念式抓住执行方式：当前 token 的表示交给路由器，选中专家计算，再把结果合起来。共享专家也参与其中。这里的专家是学出来的计算模块，模型按 token 路由。

想象有 8 个同样大小的计算分支，每次只走 2 个。你保留了 8 个分支的容量，当前 token 只执行其中 2 个。再把注意力、共享层、路由和通信的成本加上，就是理解 MoE 效率的起点。

## 细粒度与共享专家各解决什么

DeepSeekMoE 将专家划分得更细，并引入共享专家。直觉上，较细的模块提供更多组合方式；共享部分承接通用内容，让路由部分不必反复学习相同知识。

这些专家的分工是训练学出来的。观察某个专家经常在什么输入上被激活，比直接给它起名“法律专家”“编程专家”更能解释实际工作方式。这一点想清楚，读路由实验会顺很多。

## 路由失衡会把节省吃回去

如果多数 token 都挤向少数专家，其他设备空闲，热点设备排队，整体吞吐会变差。模型质量、专家容量与硬件负载因此相互牵制。

V3 报告中的无辅助损失负载均衡策略，是让路由更均衡的一项设计。具体读到不同层级的约束时，再分别看它们负责什么。这样就能看清楚，模型质量和设备负载是怎样一起照顾到的。

真正部署时，我会先看批量大小、跨设备通信和专家放置。小批量请求、慢通信、显存吃紧，都会拖住稀疏模型。激活参数告诉你一部分计算量，响应速度还得把整套运行条件算进去。

## MLA 省的是另一笔账

自回归生成通常缓存历史 token 的 Key 和 Value，避免每一步重算。上下文越长、并发越高，这份 KV cache 越显著。

V2 的 MLA 用潜在表示压缩相关缓存开销。它与 MoE 的分工不同：MoE 主要改变哪些前馈参数参与计算，MLA 处理注意力缓存等效率问题。两者互相配合，不能把它们当作同一个技巧。

一个实用判断是：机器先被什么卡住？若内存装不下，先看权重和缓存；若能装下却吞吐很低，再看带宽、通信、批处理和内核。单一“参数量”解释不了所有瓶颈。

## 数字应该放在哪个口径里

V3 报告给出总参数 671B、每 token 激活约 37B。37B 描述的是每个 token 激活的参数；部署时，整套专家权重还得存放在显存、内存或分布式设备上，随时等着路由调用。

训练成本也要分开算：报告公布的训练 GPU 小时，跟购买硬件、早期研究、失败实验、数据处理和持续服务，是不同的支出。把口径对齐以后，DeepSeek 的工程效率才有清楚的比较对象。

## R1 的推理提升为什么不能只归功于 MoE

R1 研究的是怎样利用反馈塑造推理行为，包括 R1-Zero 的直接强化学习探索，以及 R1 的多阶段流程。架构提供容量与效率，训练方法决定如何使用这些能力；两者都重要，却不是同一个解释。

如果要评估自己的业务，应选代表性任务，对比正确率、单次成功成本、延迟和人工返工量。不要仅凭“稀疏”判断便宜，也不要仅凭模型会输出较长推理就认定结果可靠。

## 读论文时的一张检查表

我推荐按这个顺序读：版本与激活方式、缓存结构、负载均衡、训练设置，最后再看实验对比。每一层都对应一笔实际成本。看懂这些，再遇到别家的 MoE，你也知道该从哪里拆。
