## “省资源”需要先说明省在哪里

LoRA、MoE、FlashAttention 都在省资源，省的位置却各不相同。一个让适配时训练的参数更少，一个让每个 token 少走一些计算分支，一个减少 GPU 数据搬运。把这三笔账拆开，技术名字就好记多了。

LoRA、稀疏 MoE 与 FlashAttention 分别提供了三个观察角度：需要更新多少参数，每次使用哪些参数，计算时怎样存取中间结果。把三项技术各自省下的资源讲清楚，选工具时就更有方向。

## LoRA：缩小需要学习的变化

LoRA 冻结原始权重，用低秩矩阵表达适配时的更新。直观上，团队不必为每个任务再保存一份完整的可训练模型，可以管理较小的适配部分。[LoRA](https://arxiv.org/abs/2106.09685)。

LoRA 保留基础模型，把需要学习的变化交给小适配器。想稳定格式、改变任务习惯，可以从适配训练入手；每天更新的新政策，则把检索资料接好。按问题安排方法，精力更容易花对地方。

我会先查错误来自哪里：资料缺失就补证据，行为不稳定再改训练或指令。把知识和输出习惯分别处理，后面也更容易知道是哪一项调整起了作用。

## MoE：每次只用部分专家

Mixtral 所描述的稀疏专家结构，在相关层通过路由选择部分专家处理当前 token。这把网络的总容量与单次实际计算区分开。[Mixtral](https://arxiv.org/abs/2401.04088)。

“专家”是神经网络模块，不是预先分配的人类职业。某个 token 用哪些专家，由训练形成的路由决定。稀疏计算可以改善容量与算量的关系，但部署还需要存储权重、调度负载和处理通信。

看 MoE，我会同时记下总参数、激活参数和运行条件。总参数关乎存放多大容量，激活参数关乎每次执行的计算，延迟与吞吐再由目标设备和负载来观察。

## FlashAttention：减少不必要的数据搬运

FlashAttention 把 GPU 不同存储层之间的读写也放进设计，用分块组织精确注意力计算。少来回搬数据，芯片就更容易把时间花在有用的运算上。这一层硬件直觉很值得弄懂。[FlashAttention](https://arxiv.org/abs/2205.14135)。

精确注意力优化不等于自动把标准密集注意力的所有成对计算改成线性复杂度。它减少某些存储与访存开销，实际收益依赖序列长度、硬件和实现。脱离这些条件说“所有请求快若干倍”，没有可比较的意义。

## 三者为何能同时出现

三者可以在同一系统里配合。适配参数、激活计算和数据搬运分别改善以后，再看瓶颈移到了哪里。算子更快，网络和排队就会更显眼，整套流程也值得一起看。

| 方法 | 主要改变 | 不能直接推出 |
| --- | --- | --- |
| LoRA | 适配时需要训练的参数 | 基础模型不再需要加载 |
| 稀疏 MoE | 每个 token 使用的专家 | 总存储与通信同比下降 |
| FlashAttention | 注意力的存储与计算组织 | 全流程延迟固定倍数降低 |

## 如何建立自己的比较口径

先固定任务集、输入长度分布、输出长度与并发，再记录首个结果等待时间、完整任务耗时和成功率。批量作业可以更重视吞吐，面对人类的交互产品则往往需要控制等待。

还应分开训练、加载、预填充和生成阶段。若只测模型已经加载后的短请求，无法说明冷启动体验；若只测长文预填充，也无法说明逐 token 生成速度。

我喜欢效率研究的地方，是它把算力变得更好用。以后再看到一个加速百分比，先问省的是哪种资源，再把任务和运行环境对上，就能更快判断它对自己有没有帮助。
