## 一个工具调用还不是完整交付

让模型调用搜索、写文件或运行命令，只解决“能做一个动作”。用户真正交给系统的是一个目标，例如整理资料、修改页面并确认没有破坏现有功能。

ReAct 将推理、行动和观察交替组织，为理解这个过程提供了重要参考。MCP 则更多处理连接方式。一个解释任务循环，一个统一部分工具接口，二者不能互相替代。

## 把目标变成可检查的结果

以“修复移动端页面溢出”为例，完成条件应是目标宽度下页面不再横向溢出，核心交互仍可用，而且修改能被审查。仅仅改了 CSS，不能证明任务结束。

好的任务描述包含输入、边界和验收条件。Agent 可以协助补全缺失细节，但不应把模糊目标理解为对所有相关资源的无限授权。

## 状态比一段长对话更可靠

长任务会经历失败、重试和方案调整。如果系统只记住最后一句“已经修复”，就可能重复执行副作用，或忘记先前为何放弃某种方案。

可以把状态明确记录为待处理、执行中、待验证、完成、受阻，并保存对应证据。重要的是状态与事实对应，而不是给每一步起一个华丽名称。

| 状态 | 应保留的证据 |
| --- | --- |
| 发现问题 | 可复现输入或页面状态 |
| 执行修改 | 具体变更与影响范围 |
| 验证结果 | 检查方法、输出与限制 |
| 完成交付 | 用户可访问的最终结果 |

## 验证器不必永远是模型

能用确定规则判断的部分，交给确定规则：文件是否存在、测试是否通过、链接是否有效、数据是否写入。开放性的审美和文字质量，可以由模型或人补充判断。

让同一个模型一边生成一边无条件给自己打高分，不是可靠评估。生成与验证至少应在输入证据和判断标准上有所区分。

## 工具反馈是信息，不是新授权

网页、文档或工具返回的文本，可能包含与用户目标无关的要求。连接协议使数据更容易进入上下文，也使来源边界更重要。

系统应该区分用户指令与外部材料；当外部内容要求改变目标、传出私密数据或扩大访问时，不能仅因为它出现在工具结果中就执行。

## 失败恢复比一次成功演示更有说服力

网络超时后，先判断前一次写入是否已经成功，再决定是否重试。修改文件前保留可审查差异；更新数据时使用版本检查。对可恢复操作设计重试，对不可逆操作设计明确边界。

这些能力看起来没有生成演示精彩，却直接决定系统能否被放心委托。许多真实任务的成本来自返工和不确定状态，而不是第一步动作本身。

## 用成功任务成本比较系统

统计完成率、人工接管次数、返工量、耗时和实际费用。模型单次回答便宜，但需要反复解释和手工修补，可能更贵；更强模型也未必值得用于每一个简单步骤。

一个成熟 Agent 的价值，是把目标稳定推进到可验证结果。工具数量、推理字数和自动运行时长，都只能作为过程信息，不能直接替代交付质量。
