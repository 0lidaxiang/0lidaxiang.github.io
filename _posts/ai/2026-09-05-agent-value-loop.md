我看 Agent，最在意的是把任务交出去之后，还要回来替它收拾多少次。能自己查资料、调工具当然让人兴奋，可交付才是我愿意继续用它的理由。

## 一个工具调用还不是完整交付

搜索、写文件、运行命令，都是 Agent 的动作。用户交给它的却是一件完整的事：资料要整理好，页面要改对，原来的功能还得能用。这里面隔着的工作，才是 Agent 产品真正要解决的。

ReAct 将推理、行动和观察交替组织，为理解这个过程提供了重要参考。MCP 则更多处理连接方式。一个解释任务循环，一个统一部分工具接口，二者不能互相替代。

## 把目标变成可检查的结果

以“修复移动端页面溢出”为例，完成条件应是目标宽度下页面不再横向溢出，核心交互仍可用，而且修改能被审查。仅仅改了 CSS，不能证明任务结束。

我的建议是把输入、允许操作的范围和验收条件一起交代清楚。缺了什么，让 Agent 主动补齐。这样你交出去的是一件有起点、有终点的事，用起来省心，出问题也知道该查哪里。

## 状态比一段长对话更可靠

长任务会经历失败、重试和改主意。只靠一段越来越长的聊天记录，最烦人的情况就是：它刚说“已经修复”，下一轮又忘了自己改过什么，甚至把刚完成的动作再做一遍。

把待处理、执行中、待验证、完成、受阻写进任务状态，再把证据挂上去。你打开任务就能看见卡在哪一步，不用从几十轮聊天里翻答案。这才是状态管理应该带来的体验。

| 状态 | 应保留的证据 |
| --- | --- |
| 发现问题 | 可复现输入或页面状态 |
| 执行修改 | 具体变更与影响范围 |
| 验证结果 | 检查方法、输出与限制 |
| 完成交付 | 用户可访问的最终结果 |

## 验证器不必永远是模型

能用确定规则判断的部分，交给确定规则：文件是否存在、测试是否通过、链接是否有效、数据是否写入。开放性的审美和文字质量，可以由模型或人补充判断。

让同一个模型一边生成一边无条件给自己打高分，不是可靠评估。生成与验证至少应在输入证据和判断标准上有所区分。

## 工具反馈是信息，不是新授权

Agent 会读到网页、文档和工具反馈，这些材料里也会混进与任务无关的指令。接入的资料越多，系统就越需要认清：哪些是你要它做的事，哪些只是它查到的文字。

系统应该区分用户指令与外部材料；当外部内容要求改变目标、传出私密数据或扩大访问时，不能仅因为它出现在工具结果中就执行。

## 失败恢复比一次成功演示更有说服力

网络超时后，先判断前一次写入是否已经成功，再决定是否重试。修改文件前保留可审查差异；更新数据时使用版本检查。对可恢复操作设计重试，对不可逆操作设计明确边界。

这些能力看起来没有生成演示精彩，却直接决定系统能否被放心委托。许多真实任务的成本来自返工和不确定状态，而不是第一步动作本身。

## 用成功任务成本比较系统

我会一起看完成率、人工接管次数、返工量、耗时和费用。一次调用省下几分钱，后面却要解释五轮、手工修三处，这样的“便宜”用起来很贵。简单步骤交给轻量模型，难点再用更强的模型，按整件事的成本算账。

我愿意把工作交给的 Agent，要能一路推进到结果，把检查做完，再把成果交到我手里。做到这里，工具调用才真正变成了生产力。
